**Phase:** 3 · **Milestone:** M3 — Plan & kalender
**Goal:** Generate a full year plan per class (thema's with their goals spread across the school year) and show it in an interactive drag-and-drop calendar — one of the two anchor screens.
**Covers FR:** FR-5, FR-6. **Constitution:** [Art. IV](../CONSTITUTION.md#article-iv--ai-is-advisory-human-in-the-loop), [Art. VIII](../CONSTITUTION.md#article-viii--tech-stack--architecture-binding-choices) (anchor screens), [Art. IX.3](../CONSTITUTION.md#article-ix--core-data-model-functional).
**UX & a11y:** this is an anchor screen — follow [`docs/ux/ui-ux-approach.md` §4](../docs/ux/ui-ux-approach.md) and [ADR-0017](../docs/adr/0017-ui-ux-design-system.md); WCAG 2.2 AA incl. keyboard-operable DnD.

- [x] **E3-02 — Spreading heuristics** — *done 2026-07-29; the claim is split into an asked half and a measured half, deliberately*
  Respect number of available blocks, logical order (e.g. seasonal thema's in season), and balanced goal distribution.
  *Done when:* generated plans place seasonal thema's sensibly and spread goals. Ref: FR-5.2.
  **The acceptance criterion as written cannot be tested, and pretending otherwise would have been the easy lie.** The AI client is a fake in every test (Art. IV.6), so "the model spreads well" is unfalsifiable here — asserting it would assert the fake. The story is therefore delivered as two halves that *are* verifiable:
  1. **Asked** — the prompt carries all three FR-5.2 properties and the figures each needs to be satisfiable: use as many different blocks as possible; a thema's `DuurWeken` must not exceed the block's weeks (so blocks now print weeks, not just days); place a season-suggesting thema in a block whose dates fall in that season; distribute the goals evenly (so each thema now prints its goal *count*, not just the codes). The block count is stated outright rather than left to be tallied. Pinned by `De_prompt_vraagt_spreiding_en_geeft_de_cijfers_die_daarvoor_nodig_zijn`.
  2. **Measured** — `Spreidingsrapport` describes what actually came back: blocks used vs available, empty periods, distinct goals per block, and any block whose thema's need more weeks than it spans. Returned on `JaarplanGeneratieResultaat` and surfaced in the UI. Seven unit tests feed it deliberately clumped and deliberately spread plans.
  *Deliberately threshold-free.* The report carries **no** pass/fail verdict and generation never retries or rejects on a bad spread (Art. IV.1) — an earlier sketch did retry until the spread passed a bar, which would have made the tool the decider and buried a model weakness in a loop. Nothing in the FA or the constitution defines an acceptable spread, so a limit in code would answer by fiat a question that belongs to the school — the same reasoning that keeps E3-10 question C open. The UI says so explicitly: *"Wat een goede spreiding is, beslist de school — de tool weigert niets."*
  *Two honest notes on seasonality.* `Thema` has **no season/period attribute**, so "seasonal thema's in season" can only come from the thema's own naam/invalshoeken plus the block's dates. The prompt is worded to reason from exactly those and still forbids outside sources (Art. IV.4) — but if the school wants this to be reliable rather than inferred, a `Thema.voorkeursperiode` field is the answer, and that is a data-model change for E6-03/directie, not something to invent here. Second, `IsOverbelast` is computed from `DuurWeken`, **not** from a thema count — three 2-week thema's fit a 6-week period, two 6-week ones do not — which is why it is a different signal from the kalender's provisional "te vol" count.
  *It is reachable from the browser, not just the API.* The kalender now carries the wireframe's **"Jaarplan genereren…"** button with the report rendered beneath it. Offering generation before E3-07 exists is safe because generation only ever *adds* proposals and never discards a decision or a lock; the destructive half (moving/removing) stays with E3-07 and its confirmation. This closes the gap E3-01's controller flagged — *"a teacher-facing screen is E3-06's job, so today this is reachable by an API client and not yet from a browser"* — which E3-06 had left open by shipping read-only.
  *A defect found by actually clicking it:* with no `AzureAI:ApiKey` set the client throws and the endpoint returns **500**, and the first version of the UI reported *"de AI gaf geen bruikbaar antwoord"* — blaming the model for a configuration fault and inviting a pointless retry loop. The UI now branches on status: 422 (model answered badly, retry is sensible) vs anything else (*"nu niet beschikbaar … meld dit aan de beheerder"*). Both state that nothing changed, which Art. IV.5 guarantees. **Worth escalating separately:** a missing API key arguably deserves a 503 from the backend rather than a 500, which would let the frontend stop inferring intent from a generic server error. Not done here — it touches E2-01's client and the shared exception handler.

  Teacher supplies parameters before generation (**bv.** vakanties, vaste momenten, gewenste startthema's).
  *Done when:* parameters measurably influence the result. Ref: FR-5.4.
  > **The `bv.` is restored to this story text on purpose (2026-07-30).** FR-5.4 reads *"De leerkracht kan parameters meegeven vóór generatie (**bv.** vakanties, vaste momenten, gewenste startthema's)"* — *bijvoorbeeld*, so the three are illustrative, not an enumerated set to implement item by item. This story's earlier wording dropped it and read as a definite list, and the implementation was then built against the paraphrase rather than the FA, which the constitution ranks above the backlog. It cost a long defence of a position the source grants in six characters. **Quote the FA when the FA is the criterion.**
  *Built (backend only, 2026-07-30) — worklog: [`worklogs/E3-04/implementation.md`](worklogs/E3-04/implementation.md).* `JaarplanGeneratieParameters` + `VastMoment`, a prompt section, `ParameterRapport`, enforcement in `JaarplanGeneratieService`, and an optional request body on `POST …/jaarplan/generatie` so the E3-02 kalender button keeps working unchanged.
  - **Vakanties are deliberately not a parameter, and the FA says so itself.** FR-12.1 assigns them to another role and another surface: *"De beheerder kan schooljaren aanmaken en de vakantie-/periodestructuur instellen."* They are persisted school data on `Schooljaar` (E3-05) and blocks are derived from it, so accepting them again would create a second source of truth for the school calendar.
  - **The structural half of that argument is narrower than first claimed.** `Schooljaar.Lesperiodes()` cuts only on `BreektPeriode`, so a **`Vakantie`** genuinely cannot be spanned by a block. A **`VrijeDag`** sits *inside* a block by design (ADR-0020 §5) and is currently **not expressed to the model at all** — and the prompt prints `Planningsblok.AantalDagen`, a raw calendar span, while `Spreidingsrapport` measures the same block in **open days**. So the model can be told a block is longer than the report will measure it, satisfy the prompt's own fit rule, and still be flagged `IsOverbelast`. That is pre-existing E3-01/E3-02 drift, **not introduced here**, but it is the load-bearing premise of this story's headline decision. **Filed as its own clause below rather than fixed in passing**, because the fix (print open-day weeks from `Schooljaar.TelOpenDagen`, the method that exists precisely because two callers disagreeing about block length was already a defect) touches the E3-02 prompt and deserves its own gate.
  - **The two parameters that do exist are different in kind, on purpose.** A *gewenst startthema* is a **preference**: it reaches the prompt and the report says whether the model complied. A *vast moment* that blocks is a **constraint**: the service refuses placements landing in its period. Enforcing the preference would mean the tool placing a thema no model proposed, leaving its provenance unstatable — `voorgesteld` would be false, and `manueel` survives regeneration and would strand a parameter the teacher had since changed.
  - **A closure is not a vast moment.** Anything that closes the school (vakantie, Hemelvaart, Pinkstermaandag, pedagogische studiedag) is a `Schoolsluiting` on the schooljaar under FR-12.1. An earlier revision listed *"pedagogische studiedag"* as a `VastMoment` example, contradicting ADR-0020 §5 outright and recreating for its neighbour the exact second-source-of-truth the vakantie exclusion was reasoned from. The boundary is now a stated rule, so a UI cannot offer two forms for one fact.

  1. **Plural `GewensteStartthemas` had single-thema semantics.** One sentence named one block for a comma-joined list, instructing the model to put several 4–6 week thema's in one themaperiode — against the system prompt's own *"zoveel mogelijk verschillende planningsblokken"* and its fit rule — and the report then guaranteed a false *"niet gehonoreerd"* entry for any teacher who named two. ### FR-6 — Calendar

- [x] **E3-05 — Planningsblok model & calendar grid** — *audited 2026-07-28 (VIOLATIONS FOUND), findings fixed, CI green 2026-07-28*
  Model the school year as configurable planningsblokken; **do not hard-assume months** — support themaperiode (4–6 wk) / subthemaperiode (~2 wk). Belgian school year Sept→June.

> ### Code-review round (2026-07-29) — seven findings on E3-06 + E3-02, all fixed
>
> Run after both stories had already merged to `main`. Every finding was verified against the code before acting; the first was reproduced with a failing test before the fix.
>
> 1. **HIGH — the jaarplan error state was unreachable.** `rooster` is chained behind the schooljaarId the jaarplan returns, so while that id is unknown the rooster query is *disabled* — and a disabled TanStack Query v5 query reports `isPending === true`. With the pending guard placed before the error guard, a failed jaarplan fetch showed *"Jaarplan laden…"* forever and `kalender.fout` was dead code. The realistic trigger is the only route into the screen today: a teacher pastes a klas-id that does not exist. Guards reordered; regression test added.
> 2. **The UI told teachers "er is niets gewijzigd" after wiping their proposal.** `VerwijderVervangbarePlaatsingen()` runs *before* the new placements are added and is persisted either way, so a valid-but-empty run deletes the previous proposal and then reported no change — false about the teacher's own data. `AantalVervangen` is now reported and rendered; the false clause is gone. (The 422/500 messages keep it, where it is true.)
> 3. **The spreading report counted rejected placements.** `IsVervangbaar` is `Voorgesteld && !Vergrendeld`, so `Geweigerd` survives regeneration — and was making a period count as *used*, and even as *overbelast*, on the strength of a thema the teacher had thrown out. New domain predicate `Themaplaatsing.IsGepland`; the kalender's "te vol" count applies the same rule (the card is still shown — visible, not counted).
> 4. **The two screens disagreed about how long a period is.** The report divided the raw calendar span by 7 while the ribbon used **open days**, so a 5-week thema could be reported as fitting a period the screen beside it called 4,9 weeks. Counting now lives in one place, `Schooljaar.TelOpenDagen`, used by both.
> 5. **`?niveau=99` returned 500.** ASP.NET Core binds any integer to an enum, so it passed model validation and threw unmapped in the seam — on a public GET. Now a 400; the named form always 400'd, which is why only the numeric form is asserted.
> 6. **The seeder guarded the klas name but not thema names.** `Thema.Naam` is not uniquely indexed, so a collision throws nothing — it silently creates a second "Water", and generation resolves the model's answer *by name* (`g.First()`), which would bind a developer's plan to the demo thema and make their own unreachable. Colliding names are now skipped, carrying each thema's block index with it so the layout cannot shift.
> 7. **The plural bug was fixed as a class, not an instance.** Four more strings rendered "1 thema's voorgesteld" / "1 bestaande plaatsingen bleven staan" — and a test *pinned* the ungrammatical one, so fixing the copy would have looked like a regression. Added `tAantal(aantal, enkelvoud, meervoud)` to the i18n helper and routed all five call sites (including the earlier `herzienTitel` ternary) through it.
>
> *Two of these are worth remembering beyond their fix.* A disabled query reporting `isPending` makes guard **order** load-bearing, not stylistic. And a test that pins wrong user-facing copy is worse than no test: it defends the defect.
