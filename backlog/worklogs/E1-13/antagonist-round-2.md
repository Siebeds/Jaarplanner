## Findings

### [MINOR] 1. The new neutral 409 frame asserts "er is niets gewijzigd" on the commit path, which is the exact claim this same round decided a client may not make
- **Article/FR:** Art. II.3 (a message must not assert what its author cannot know); Art. IV.2; Art. X.5
- **Where:** `frontend/src/i18n/nl.json` → `import.opstap.geweigerdAlgemeenUitleg`; chosen at `frontend/src/features/import/Opstapimport.tsx:145-157`, rendered at `:253`; the justifying comment at `:139-143`
- **Problem:** MINOR 5's fix concluded, correctly, that "Er is niets gewijzigd" is knowable on a preview and a guess on a commit, and introduced `import.onbeschikbaarNaDoorvoeren` for exactly that. The refusal panel does not get that treatment: `isWeigering` (`:124`) is true for a 409 on **either** path, and the unclassified branch renders *"het bestand is als geheel geweigerd en er is niets gewijzigd."* — a data-state claim, on the commit path, about a refusal whose cause the screen has just admitted it cannot identify. The comment defends it as "what a 409 always guarantees (the file was refused as a whole, nothing changed)". HTTP guarantees no such thing; 409 carries no statement about whether a write occurred. Reachability today is low (all three `OpstapImportFoutSoort` members map to a recognised URI, and each rolls back), so the practical falsity needs a replaced body or a future undiscriminated refusal — which is precisely the case the frame was written for.
- **Required fix:** drop the "en er is niets gewijzigd" clause from `geweigerdAlgemeenUitleg`, or select a commit-path variant of it as the non-409 branch already does. Correct the comment's "what a 409 always guarantees".

### [MINOR] 2. The cap notice's advice, and the new comment asserting why it is true, hold only on the create path
- **Article/FR:** Art. II.3 (actionability); Art. X.5 (a comment asserting an untrue invariant)
- **Where:** `backend/src/Jaarplanner.Infrastructure/SchoolcontentImport/SchoolcontentImportService.cs:487-493` (comment), `:515-519` (copy), reached from `:457` with `reedsAanwezig: behouden`
- **Problem:** the comment states *"the codes that fit are the **first** ones in the file's `Themadoelen` cell (`Take(ruimte)` below), so the sentence says to put the anchoring ones first."* That is true from `:193` (`reedsAanwezig: 0`), and false from `:457`, where `ruimte = 3 - behouden` and `behouden` counts links retained from the database — including the teacher-set `aanvaard`/`manueel` decisions Art. IV.2 preserves. With a thema holding two preserved decisions and a file listing three new codes, the notice tells the reader to reorder a column that can only ever decide which **one** of their three lands; the real blocker is two slots the file does not control, which the sentence never mentions. The advice is incomplete rather than contradictory, but the comment is factually wrong at one of its two call sites, and this notice is the one the round was fixing for being written past its reader.
- **Required fix:** either say what a teacher can actually do when slots are occupied by retained links (remove the stale themadoel, or use the discard opt-in), or scope the sentence to the create path and give the reconcile path its own; and correct the comment's claim to name `reedsAanwezig`.

### [MINOR] 3. The copy guard's own stated blind spot lives only in the worklog, and the file where the newest defect was found has no guard at all
- **Article/FR:** Art. X.1 (relevant tests), Art. X.5; the story's own MAJOR-4 lesson
- **Where:** `backend/tests/Jaarplanner.UnitTests/Schoolcontent/SchoolcontentImportOpmerkingenTests.cs:41-47` and its class docstring `:10-36`; the fixed-but-untested notice at `backend/src/Jaarplanner.Infrastructure/OpstapImport/OpstapImportService.cs:159-183`

The round established by reading that a **fourth** predicate class exists (a composed singular, `"De 1 bestaande doelen blijven ongewijzigd"`) which those three cannot catch. That limitation is written in `implementation.md:123-125` and `backlog/README.md`, and nowhere a future author of a notice will meet it — the helper still reads as a complete predicate set. (b) The fifth defect was in `OpstapImportService`, and there is **no test anywhere** asserting either grammatical form of that notice: I grepped the whole test tree for `bestaande doel(en) blijft/blijven` and `geen geldige leerplandoelen` and found only the production file. The +3 backend tests are all in the schoolcontent guard. So the two Op.stap notices this screen renders have neither a copy guard nor a case, one round after a copy defect was found in one of them. That is the selective-fix pattern the round diagnosed, one file over.

### [MINOR] 4. The new E3-06 guard on the Op.stap half is one-sided: a first import that reads nothing still gets a commit control
- **Article/FR:** the E3-06 rule as `CLAUDE.md` states it ("never ship a control that does nothing"); Art. X.5
- **Where:** `frontend/src/features/import/Opstapimport.tsx:127-128` and `:295-299`, against `backend/src/Jaarplanner.Infrastructure/OpstapImport/OpstapImportService.cs:155-183`
- **Problem:** `nietsInTeLezen` keys on `diff.overgeslagen`, and the Op.stap service sets that only when `inkomend.Count == 0 && bestaand.Count > 0` (`:159`) or the discipline is out of scope (`:132`). The first-import case falls through: a header-only or all-empty-rows workbook (the parser skips fully empty rows silently, `ClosedXmlOpstapParser.cs:14`) for a discipline with no goals loaded yields `overgeslagen: false`, no opmerkingen, both verdicts green, *Doelen inlezen* offered, and afterwards *"Dit bestand is volledig ingelezen"* plus *"De doelen zijn ingelezen"* for zero doelen. Edge-case and unreachable for a real Op.stap file while E1-12 is open, but it is the very state the new guard was written to remove, and the guard reads as if it covers it.
- **Required fix:** either widen the server condition (absence of input is a no-op whether or not rows exist already) or gate the frontend on `overgeslagen || diff.isLeeg && nothing added` at the one place; alternatively record the hole where the guard is, so the next reader does not read it as total.

### [MINOR] 5. `import.opstap.voorwaarde` hard-codes a claim about database state whose expiry is owned only by a code comment
- **Article/FR:** Art. X.5; MINOR 8's own remit (the screen must state the prerequisite *and* stay true)
- **Where:** `frontend/src/i18n/nl.json` → `import.opstap.voorwaarde`; rendered unconditionally at `frontend/src/features/import/Opstapimport.tsx:186-188`; the removal owner named only at `:182-184`; `backlog/E1-curriculum-content.md:104-108` (the E1-12 story) says nothing about it
- **Problem:** the notice asserts *"De decretale minimumdoelen zijn nog niet ingeladen"* as fact, with no check behind it. The moment E1-12 lands, a screen states the opposite of the truth until somebody deletes a string, and the only record of that obligation is a comment in a component. This repo's documented failure mode is exactly claims that go stale because the story that invalidated them never read them (round 1's MINOR 7 was that, through a merge). I accept there is no `Minimumdoel` read endpoint today (I checked the controller set), so deriving it is not free — which is why this is MINOR and not MAJOR.
- **Required fix:** add the removal of `import.opstap.voorwaarde` and its block to the **E1-12 story's** *Done when*, so a backlog item owns it; or derive the notice from a count once E1-12 adds one.

### [QUESTION] 6. The reset can now discard an FR-2.5 review report the reader still needed
- **Article/FR:** Art. III.4 / FR-2.5 (the tool flags what must be reviewed); Art. XIV (the durable-acknowledgement decision the story already surfaced)

- **What I would need to settle it:** a directie answer on whether a `verdwenen` report must be re-readable at all (round 1's open question 1). If yes, this belongs to that story; if no, the current behaviour is correct and this is closed by decision.
