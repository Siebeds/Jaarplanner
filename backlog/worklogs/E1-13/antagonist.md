## Findings

### [MAJOR] After a commit, "nakijken" fires a request whose answer can never appear
- **Article/FR:** Art. X.5/X.6 consistency; the E3-06 rule in `CLAUDE.md` ("never ship a control that does nothing"); FR-1.3 / FR-2.5 (the preview must describe the run in front of the reader)
- **Where:** `frontend/src/features/import/Schoolcontentimport.tsx:105` and `:81-92`; identically `frontend/src/features/import/Opstapimport.tsx:86` and `:68-76`
- **Problem:** the displayed outcome is `const uitkomst = commit.data ?? voorbeeld.data;`. `kijkNa()` calls only `voorbeeld.mutate(...)`; it never calls `commit.reset()`. After a successful commit `commit.data` is set and wins forever, while the form stays enabled (`disabled={!bestand || bezig}` → enabled: the file is still selected, `bezig` is false). So a teacher who presses **Bestand nakijken** after an import sees the button change to "Bezig met nakijken…", a real `POST …/voorbeeld` goes out, and then the screen shows exactly the previous *commit* panel again ("De import is doorgevoerd." / "De doelen zijn ingelezen.") with the new preview discarded. The same holds for the Op.stap half, where the discarded answer is the FR-2.5 review report itself. If the database changed between the two, the screen is asserting a stale report while the reader believes they just refreshed it. Re-clicking the already-selected radio does not fire `onChange`, and re-picking the same file is browser-dependent, so on this path there is no reliable escape short of choosing a different file.
- **Required fix:** reset the commit mutation when a new preview starts (`commit.reset()` in `kijkNa`), or derive `uitkomst` from whichever run is the more recent rather than from a fixed precedence. Pin it with a test: preview → commit → preview again → the fresh preview is what is on screen.

### [MAJOR] The 409 framing copy contradicts the refusal it frames, for one of the two 409 cases
- **Article/FR:** Art. II.3 (a message must be actionable by its reader); FR-2.1/2.5; the story's own clause-6 brief ("Distinguish the two on screen")
- **Where:** `frontend/src/features/import/Opstapimport.tsx:165-179`; `frontend/src/i18n/nl.json` → `import.opstap.geweigerdUitleg`
- **Problem:** the story was warned that 409 conflates *"the application is not ready for this file yet"* (E1-12) with *"this file belongs to another discipline"*. The implementation branches 409 vs 400 and applies the system-state frame to **both** 409s unconditionally. `import.opstap.geweigerdUitleg` reads: *"Dit gaat niet over de rijen in het bestand. De toepassing kan dit bestand nog niet inlezen, en hieronder staat waarom en wat er eerst moet gebeuren."* For the wrong-discipline refusal the server's own `detail`, printed two lines below, is `backend/src/Jaarplanner.Application/Curriculum/Import/OpstapImportFout.cs:135-142`: *"Deze codes staan al bij een andere discipline: … Controleer of dit bestand bij discipline {n} hoort."* That is precisely *about* specific codes in specific rows of the uploaded file, and the fix is the uploader's, not the system's. The screen therefore prints two mutually contradictory sentences and tells the reader to wait for a system change when what is wrong is their discipline number.
- **Required fix:** key the frame on which 409 it is. The refusals already have distinct shapes in `OpstapImportFout`; either expose a discriminator (a `type` URI, an error code, or a distinct `title`) and branch on it, or narrow `geweigerdUitleg` so it makes no claim the second case falsifies and let the `detail` carry the whole diagnosis.

### [MAJOR] `/import` is flagged directie-only, and E1-13 put a leerkracht-facing importer on it
- **Article/FR:** Art. VI.1 (permissions are role-based per the §3.2 matrix); FA §3.2; FR-1.1
- **Where:** `frontend/src/app/routes.ts:79-93`; `frontend/src/features/import/ImportPagina.tsx:14-17`

### [MINOR] "Er is niets gewijzigd" is asserted on the commit path, where the client cannot know it
- **Article/FR:** Art. IV.2 / III.4 (a destructive outcome must never be misreported); Art. II.3 (actionability)
- **Where:** `frontend/src/i18n/nl.json` → `import.onbeschikbaar`; render sites `Schoolcontentimport.tsx:205` and `Opstapimport.tsx:187`
- **Problem:** one string serves both the preview and the commit. On the preview it is trivially true. On the commit it is a guess: the import is a single `SaveChangesAsync` (`SchoolcontentImportService.cs:119`, `OpstapImportService.cs:280`), so an exception the app raises does indeed roll back, but a 200 whose body cannot be parsed (`apiFetch` then throws a `SyntaxError`, not an `ApiError`), a gateway 502/504 after the save, or a dropped connection all land on this copy after the write happened. ### [MINOR] A ticked discard opt-in survives a re-preview

## Engaged with, and not raised as findings

**The pre-selected `Toevoegen` radio (deliberate departure from E3-04's rule).** I accept the argument, on its own terms rather than by deference. Three things make it different from E3-04: the default is the *non-destructive* option, it matches the server's own default (`SchoolcontentImportController.SchoolcontentImportInvoer.Modus ?? Toevoegen`), and nothing is written until a separate preview-then-commit gate is passed, so a pre-selection cannot cause loss. The rule's real content — that the choice must be legible without prose above it — is honoured: each label states what it does to existing content (`modusToevoegen`, `modusBijwerken`), and the diff heading changes with the mode so the consequence is visible in the preview. The residual risk is a teacher re-importing an updated file who never reads the radio: their updates are silently *not applied*. That is legible (`"Wat dit bestand toevoegt"`, `0 bijgewerkt`) and non-destructive, so I do not call it a violation.

**`vereistReview` is correctly *not* used.** `Opstapdiff.Verdwenen` derives the notice from `verdwenen` + `verdwenenMaarGekoppeld` and scopes the copy to the run (`import.opstap.verdwenenTitel`: *"Nazicht bij deze inlezing…"*), with two tests pinning both halves of the trap. The E3-09 mistake is not reproduced. `vereistReview` survives in `types.ts:194` as a documented, unused contract field with a warning attached, which is the right place for it.

**`KolomLabel` is defensible against Art. III.3.** It is derived (`SchoolcontentRijProbleem.cs:35`) from `SchoolcontentKolommen.Label`, the same single source the parser (`ClosedXmlSchoolcontentParser.cs:148,165,177,193,234`) and the template generator (`:69`) read. A frontend enum-name→label table would have been a second copy of the sheet layout. It is not UI copy escaping `nl.json` either: it is a heading out of the teacher's own file, and the framing around it (`import.kolom`) does come from the catalogue.

**No new hue, and the contrast reasoning holds.** `Schoolcontentdiff` gives `Toegevoegd`/`Bijgewerkt`/`Ongewijzigd` a sign (`aria-hidden`) plus the word plus weight, no colour. `Verdicten` reuses `suggestie-geweigerd`, `attentie` and `petrol-wash` only, each with a glyph and a word. I recomputed the `--input` claim myself from `index.css`: `hsl(40 14% 52%)` against `paper-diep` `hsl(40 20% 94%)` gives **2.998:1**, against `card` **3.391:1** — so the stated 3.01 / 3.40 are right and moving the Op.stap form onto `bg-card` is the correct call, not taste. I also composited the surfaces nobody named: `text-suggestie-geweigerd` on `bg-suggestie-geweigerd/10` over `paper-diep` = **4.96:1**; `text-ink-zacht` on `paper-diep` = **5.34:1**; `text-ink-zacht` on `attentie-zacht` = **5.70:1**. All clear AA for their sizes. I could not run a real browser, so these are computed values, not measurements; they agree with the worklog's browser numbers where they overlap.

That is the right seam while the "which disciplines first" decision is open, and it does not hard-assume an answer — recorded so nobody later mistakes the free-text field for a deliberate product choice.
